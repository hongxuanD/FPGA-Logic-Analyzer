# 项目生命周期与阶段计划（MAN.3）

ASPICE 不规定用哪种生命周期模型，只要求**定义一个与项目规模相称的模型并按它管理**。
本文件即该定义。

需要澄清一个常见误读：**V 模型那张图表达的是工作产物之间的追溯关系，不是时间轴。**
它没有要求左侧全部完成才能开始右侧。增量开发中每个增量都自己走一遍完整的 V，
只是每次覆盖的范围较小。

## 文档与实现的关系

**架构写完整，实现按阶段走。**

`docs/sys3/` 和 `docs/swe2/` 需要覆盖完整架构，因为接口和模块边界改起来代价大，
一次定对比事后重构便宜。但**详细设计与实现只先做阶段 1 的子集**，
不要等全部设计文档铺完再动手。

理由很具体：`../man5/MAN5-risk-register.md` 中过半的风险，确认时机都是阶段 1。
杜邦线信号完整性、UART 是否丢字节、主机端波特率支持——都要有真实硬件跑起来
才能验证。若按完整设计一次做完，这些风险会在最后集中爆发，而那时架构已经定死。

阶段 1 的结果还应当反过来检验架构：若 I3 的顺序流接口在实现时别扭，
此时修订 SWE.2 仍然便宜。

## 阶段划分

阶段顺序由 **SUMP 的命令集**驱动：PulseView 能问什么，就是值得做什么。
这个安排把协议实现分散到各阶段，而不是堆在最后。

### 阶段 1：采集通路与 SUMP 最小子集

目标是**在 PulseView 中看到真实采集数据**。固定采样率、固定深度、无触发。

建议按三小步推进，每步都能独立验证：

| 步骤 | 内容 | 验证了什么 |
| --- | --- | --- |
| 1a | 只应答复位与 ID | UART 收发、波特率、命令解析框架。**采样器一行未写**，PulseView 的设备列表中即可出现本设备 |
| 1b | 收到 Run 后吐一段**已知的合成数据**（如递增计数或走马灯） | 上传通路、每样本字节数、通道映射、流控、长度约定。**全部在接入真实采样之前完成** |
| 1c | 把合成数据换成真实采样 | 唯一的新变量是采集通路本身 |

1b 这一步尤其重要：用自己造的数据验证上传格式是否符合 PulseView 的预期，
比先接真采样再排查要清楚得多。

涉及的 SUMP 命令：`0x00` 复位、`0x02` ID、`0x04` metadata、`0x01` Run、样本转储。

交付的需求：`SYS-001` `SYS-002` `SYS-003` `SYS-006` `SYS-007` `SYS-008`
`SYS-010` `SYS-011` `SYS-012` `SYS-013` `SYS-014` `SYS-015`。

### 阶段 2：触发与触发前采样

环形缓冲、触发判定、触发前保留比例。

涉及的 SUMP 命令：`0xC0`–`0xC5` 触发掩码／值／配置、`0x81` read & delay count。

交付的需求：`SYS-004` `SYS-005`。

### 阶段 3：采样率与通道组可配

采样率分频、通道组选择。

涉及的 SUMP 命令：`0x80` 分频、`0x82` flags。

交付的需求：`SYS-009`。

## 为什么 SUMP 不再是独立的最后阶段

早期计划把 SUMP 排在第四阶段，理由是「由简到繁」。**那是一个默认套路，
不是针对 SUMP 的难度分析**，而且结论是错的。

按难度看，SUMP 是几百行 VHDL，与一个中等规模的状态机相当，算法上没有难点。
真正棘手的是三处**琐碎且失败不透明**的地方：

1. **字节数契约。** 主机按 read count 和 flags 算出应收字节数，多发或少发一个，
   后续全部错位。
2. **命令长度解析。** 把单字节命令误判为五字节命令，会吞掉后续四个字节，
   从此永久失步。
3. **失败几乎没有诊断信息。** PulseView 只会报找不到设备，或显示垃圾波形。

第三条看似支持推迟，实则相反：**这类问题应当在系统最简单的时候解决。**
若放到最后，采样器、触发器、缓冲都已在运行，出错时有五六个可能来源。
1a／1b／1c 的拆法让每一步的失败都可定位。

推迟还有一项隐性成本：需要一套过渡的调试转储和配套上位机脚本，
这些工作最终都要丢弃。提前实现 SUMP 后，写下的每一行都是最终接口。

## 排期方法的教训

阶段划分不应凭「由简到繁」的直觉，而应对每个部分回答四个问题：

- 这部分有多难？
- 它的失败模式好不好诊断？
- 它依赖什么、被什么依赖？
- 先做能省掉什么、后做会浪费什么？

SUMP 的答案是：不难、失败不好诊断、不依赖别的、被所有东西依赖、后做会浪费一套
过渡工具。**四条全部指向早做。**

## 后续可能的方向

以下不属于当前范围，也没有对应的系统需求，记录以备将来评估：

- **游程编码（RLE）**：对空闲期长的信号可显著延长有效采集时长。
  注意 sigrok 的 `ols` 驱动在 RLE 处理上有已知互操作缺陷。
- **串行模式触发**：触发在某个特定命令字节上，需要在触发路径中做移位与字节对齐，
  是全系统唯一与协议相关的功能。
- **状态模式采集**：以被测时钟为采样时钟，深度可提升十倍以上，代价是丢失时序信息。
