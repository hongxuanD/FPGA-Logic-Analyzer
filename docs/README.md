# 文档索引

按 ASPICE 的过程划分子目录。这是**轻量适配**：借用分层、可追溯、每层配验证
这三个核心做法，文档用自然语言写，不套官方模板，不做能力等级评估。

## V 模型对照

左侧逐层分解，右侧逐层验证，**同一层左右相互对应**——右边每个过程验证的正是
左边同层的产物。

| 目录 | 过程 | 回答什么问题 | 对应的验证 |
| --- | --- | --- | --- |
| `sys1/` | SYS.1 需求获取 | 干系人想要什么 | — |
| `sys2/` | SYS.2 系统需求分析 | 系统对外表现如何 | `swe6/` 之上的系统合格性测试（SYS.5） |
| `sys3/` | SYS.3 系统架构设计 | 分成哪几块，怎么连 | 系统集成测试（SYS.4） |
| `swe1/` | SWE.1 软件需求分析 | 各子系统要做什么 | SWE.6 合格性测试 |
| `swe2/` | SWE.2 软件架构设计 | 分成哪些组件，接口是什么 | SWE.5 集成测试 |
| `swe3/` | SWE.3 详细设计与单元构建 | 每个单元内部怎么实现 | SWE.4 单元验证 |
| `swe4/` | SWE.4 单元验证 | — | — |
| `swe5/` | SWE.5 集成与集成测试 | — | — |
| `swe6/` | SWE.6 合格性测试 | — | — |
| `traceability/` | 追溯矩阵 | 每条需求落到哪个组件、哪个测试 | — |

FPGA 的 RTL 落在 SWE 还是 HWE 在 ASPICE 4.0 里有歧义。本项目按 SWE 处理，
因为开发流程（源码、版本管理、仿真验证）更接近软件。

## 需求编号

| 前缀 | 含义 | 所在文档 |
| --- | --- | --- |
| `STK-nnn` | 干系人需求 | `sys1/` |
| `SYS-nnn` | 系统需求 | `sys2/` |
| `CON-nnn` | 约束（外部条件或开发约定，不参与功能追溯） | `sys2/` |
| `FPGA-nnn` | FPGA 子系统需求 | `swe1/` |
| `HOST-nnn` | 上位机子系统需求 | `swe1/` |

每条需求带三个属性：**来源**（上一层的 ID）、**验证方法**、**阶段**。

判断需求是否合格的唯一标准：**能不能写出它的验证方法。** 写不出来说明还没定义清楚。

## 文件命名

每份文档的文件名以其所属过程为前缀，即使已经放在对应的子目录下：

```text
sys1/SYS1-stakeholder-requirements.md
sys2/SYS2-system-requirements.md
swe1/SWE1-fpga-requirements.md
swe1/SWE1-host-requirements.md
```

前缀是冗余的，但编辑器标签页只显示文件名不显示路径。同时开七八个文档时，
`SYS2-system-requirements.md` 一眼能定位，`system-requirements.md` 不能。

一个过程下可以有多份文档（如 `swe1/` 会分 FPGA 侧和上位机侧），
用后半段的描述性名称区分。

本文件保持为 `README.md`，因为它是目录索引而非过程产物，
且这个名字在 GitHub 上会自动作为目录首页渲染。

## 管理类过程

阶段划分和风险不属于 SYS/SWE 那两列。ASPICE 把它们放在管理过程里：

| 目录 | 过程 | 内容 |
| --- | --- | --- |
| `man3/` | MAN.3 项目管理 | 生命周期模型定义、阶段划分 |
| `man5/` | MAN.5 风险管理 | 风险登记册，含已关闭的条目 |

需要注意 ASPICE **不是开发方法论**，它是过程评估模型：只要求「定义一个与项目
规模相称的生命周期并按它管理」，不规定该用瀑布、V 模型还是增量。
「计划—监控—调整」属于能力等级 2 的属性，横向作用于所有过程，不是某个单独的盒子。
