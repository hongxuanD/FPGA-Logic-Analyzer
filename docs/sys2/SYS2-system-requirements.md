# 系统需求（SYS.2）

把 `../sys1/SYS1-stakeholder-requirements.md` 里的原始诉求转换成**可验证**的条目。

判断一条系统需求是否合格的标准只有一个：**能不能写出它的验证方法。**
写不出来说明这条还没定义清楚，应该继续拆。

## 表格约定

- **来源**：本条派生自哪条干系人需求，用于向上追溯。
- **验证方法**：`检视`（读文档或代码确认）、`分析`（看工具报告，如资源占用）、
  `仿真`（testbench）、`实测`（连实际硬件）、`演示`（端到端走一遍）。
- **阶段**：由 `../../PROJECT_CONTEXT.md` 中哪个实施阶段交付。

## 派生说明

几条需求的数值不是拍脑袋定的，记录推导过程以便日后调整时知道动了什么。

**`SYS-003` 为什么是 100000 个样本**

`XC7A35T` 有 50 个 36Kb BRAM，合计 225 KB。8 通道每样本 1 字节，理论上限约
200K 样本，但那要占满全部 BRAM，不留任何余量给其他逻辑和跨时钟缓冲。

按 100K 样本立需求，占用约一半 BRAM，留出充分余量。在 SCK = 8 MHz 时，
一个 SPI 字节耗时 1 µs 即 100 个样本，100K 样本对应 **约 1000 字节**，
覆盖 `01` 中「几十到几百字节」的典型传输规模。

若日后确实需要更长的采集窗口，优先考虑游程编码或状态模式采集，
而不是把 BRAM 占满——见 `../../PROJECT_CONTEXT.md`。

**`SYS-007` 为什么是 3 秒**

100K 样本即 100 KB。按 8N1 每字节 10 位计算：

| 波特率 | 有效吞吐 | 传 100 KB 耗时 |
| --- | --- | --- |
| 115200 | 11.5 KB/s | 8.7 s |
| 921600 | 92 KB/s | 1.1 s |

**这条需求直接排除了 115200。** 波特率提升不是优化项，是满足 `SYS-007` 的必要条件。
3 秒的取值来自 `STK-005`：等待不应打断调试思路，秒级可接受，十秒级不可接受。

**`SYS-015` 为什么这样写**

上传链路是裸 8N1 串口。若上位机来不及取走数据，FT2232HQ 的接收缓冲溢出即丢字节。
丢一个字节后全部错位，解码出的是看似合理的垃圾——**拿着错数据分析，
比明确的失败更危险**。这是需要这条需求的原因。

本条**只描述性质，不指定手段**，因为可行的手段不止一种：

| 手段 | 性质 | 可用性 |
| --- | --- | --- |
| XON/XOFF 流控 | 预防丢失 | SUMP 协议原生支持，见下 |
| 帧序号 + 校验 | 检测丢失 | 需自定义协议 |
| 主机请求分块的握手 | 预防丢失 | 需自定义协议 |

早期草稿曾把本条写成「丢失应可被检测」，那实际上排除了流控这个更好的方案。
**需求描述性质、架构选择手段**——这条边界值得留意，写死机制会过早锁死实现。

具体选哪种属于 SYS.3 和 SWE.2 的范围。风险分析见 `../../PROJECT_CONTEXT.md`。

**`SYS-014` 会反向约束上传协议**

要求在 PulseView 中查看，实际含义是实现 sigrok 的 `ols` 驱动所使用的 **SUMP 协议**。
这是一条**外部接口约束**：上传协议因此不再是可自由设计的部分。

从 sigrok 官方 wiki 核实的 SUMP 行为（2026-08-12）：

- **数据阶段没有任何完整性机制。** 「发送采集数据时，分析仪发送 4 字节为一组的块，
  不存在起始或结束序列」，主机靠超时判断传输结束。因此 SUMP 模式下无法用校验
  满足 `SYS-015`。
- **但 SUMP 支持 XON/XOFF 流控**（`0x11` / `0x13` 属于命令集）。主机可在上传途中
  叫停设备，从而**预防**缓冲溢出——这是 SUMP 模式下满足 `SYS-015` 的途径。
  相应地，FPGA 在发送期间必须保持接收通路活跃，这是对 SWE.2 的一条约束。
- **RLE 与 sigrok 存在已知互操作缺陷**：sigrok 传入的样本数被 OLS 理解为压缩后的
  样本数。若阶段 3 引入 RLE 并希望同时支持 PulseView，需要绕开这个问题。

- **波特率默认 115200，但可以覆盖。** libsigrok 的 `ols` 驱动中
  `#define SERIALCOMM "115200/8n1"` 只是缺省值，`SR_CONF_SERIALCOMM` 选项可以改写。
  命令行形式为：

  ```bash
  sigrok-cli --driver ols:conn=COM3:serialcomm=1000000/8n1
  ```

  因此 `SYS-007` 的 3 秒指标在 SUMP 模式下可以满足，但**连接时必须显式指定波特率**，
  用默认值会退回 115200 即 8.7 秒。这一点应写进使用说明。

仍未核实：**PulseView 的图形界面是否暴露 `serialcomm` 选项**。`sigrok-cli` 确定支持，
若 GUI 只提供串口下拉框，则需从命令行启动或修改配置文件。

**`SYS-004` 的措辞经过两次收敛**

最初草稿是「以任一通道的**下降沿**触发」。那是把一个具体用法写成了需求——
下降沿之所以常用，只是因为 SPI 片选低有效。实际需要上升沿的场景不少：

| 信号 | 有用的边沿 |
| --- | --- |
| `CS_N` | 下降沿表示传输开始，**上升沿表示传输结束** |
| `HELIOS_CE` | **上升沿**，用于观察 SR150 的上电与复位时序 |
| `HELIOS_GPIO5_HOST_INT` | 取决于该信号的有效极性，可能是上升沿 |
| 其他设备的高有效片选 | **上升沿** |

第二次修改把「多通道电平组合匹配」并入同一条，而不是另立一条需求，
因为**两者是同一个机制**：

```vhdl
-- 带掩码的组合比较，得到匹配信号
match   <= '1' when ((sample xor trig_value) and trig_mask) = zeros else '0';
-- 触发在匹配信号的上升沿，而非匹配为真的整段时间
trigger <= match and not match_d;
```

第二行就是边沿检测，只是输入从单根信号换成了所有通道的组合判断结果。
单通道边沿是它的特例：掩码只选该通道、值设为目标电平，
匹配信号的上升沿即该通道的对应边沿。

**组合匹配能表达单通道边沿，反之不能**，因此写成一条能力更准确，
也避免架构阶段误做成两个模块。

组合匹配在本项目的实际用途：

| 场景 | 条件 |
| --- | --- |
| 只抓发往 SR150 的传输 | `CS0=0` 且 `CS1=1` |
| 抓异常状态 | `CE=0` 但 `CS0=0`，芯片未使能却被选中 |
| 中断置位期间的传输 | `HOST_INT=1` 且 `CS0=0` |

**不包括**「触发在某个命令字节上」。SPI 的数据是串行的，
某一采样时刻只有一个比特，无法用瞬时组合匹配一个字节。
那需要在触发路径里做移位与字节对齐，本质上是一个迷你 SPI 接收器，
属于独立特性，当前不在范围内。

因此来源同时列入 `STK-002`——把传输放在上下文里看，需要能触发在控制线上，
而控制线的有效极性和组合方式都不由本系统决定。

**`SYS-002` 为什么是 100 MSa/s**

从需要的过采样倍数正推，而不是从板载晶振反推。

逻辑分析仪异步采样一个同步协议时，采样率决定了边沿位置的分辨精度。
业界经验值是 **4 倍为理论下限、10 倍为舒适区**。以 10 倍为基准：

| 过采样倍数 | 8 MHz SCK 下所需采样率 | 边沿位置不确定度 | 占周期比例 |
| --- | --- | --- | --- |
| 4x | 32 MSa/s | ±31 ns | 25% |
| **10x** | **80 MSa/s** | ±12.5 ns | 10% |
| 12.5x | 100 MSa/s | ±10 ns | 8% |

因此需求下限是 **80 MSa/s**。板载晶振为 100 MHz，直接满足且留有 25% 余量，
同时**不需要 PLL**，省掉一个时钟域和一处潜在的时序收敛问题。

需求写成「不低于」而非「等于」，是为了将来提高采样率时不必修改本条。
8 MHz 这个输入取自首个验证目标，也与已核实的 QN9090 实际配置一致。

**采样率带来的固有局限：最小可检测脉宽**

过采样倍数决定「能否正确解码正常信号」，最小可检测脉宽决定「能否发现异常信号」，
两者是不同的性质，需求容易只写前者而漏掉后者。

100 MSa/s 意味着采样间隔 10 ns，**窄于 10 ns 的脉冲可能完全不被采到**。

这与风险表第一条直接相关：杜邦线上的振铃产生的毛刺很可能就窄于 10 ns，
也就是说**若真出现该类问题，本系统未必能观察到它**。判断信号完整性是否达标时
不能只依赖本系统自身的采集结果，还应结合解码是否出错、以及必要时用示波器交叉验证。

提高最小脉宽分辨能力需要更高采样率（商用设备标称的「2 ns 窄脉冲捕获」对应
500 MSa/s 级别），当前不在范围内。这是已知且接受的局限，不是缺陷。

## 未决事项

以下需求的可满足性依赖尚未核实的事实。**在核实之前，相关需求视为暂定。**

| 需求 | 依赖的未确认事实 | 影响 |
| --- | --- | --- |
| `SYS-007` | 板载 FT2232HQ 实际可用的最高波特率 | 若达不到 921600，需重新评估 3 秒指标或引入数据压缩 |
| `SYS-003` | 布线后 BRAM 实际可用于采集缓冲的比例 | 若不足，需下调样本数 |
| `SYS-002` | 杜邦线在本套装配下的实际边沿速率上限 | 若低于预期，采样率可用但被测 SCK 上限需下调 |

核实进展记录在 `../../PROJECT_CONTEXT.md` 的「待确认的事实」一节。

**已解除的一项。** 后续应用目标（QN9090 与 SR150）的 SPI 速率原本是未知量。
2026-08-12 查阅生产固件确认为 **8.000 MHz、SPI Mode 0**，与首个验证目标一致，
因此本文件按 8 MHz 推导的全部数值对两类目标同时成立，不需要屏蔽探头或
`ISERDESE2` 过采样。

由此产生一条对 `SYS-001` 的补充依据。被测总线上**只有 SR150 一个从设备**，
SPI 四线（`SCK` `MOSI` `MISO` `CS_N`）即可覆盖传输内容；此外值得采集 SR150 的
控制线，尤其是**主机中断线**——它说明主机为何在某个时刻发起传输。

合计 **6 至 7 路**，`SYS-001` 要求的 8 通道留有 1 至 2 路余量。
控制线在实物板上是否有可接入的测试点尚未核实，若不可接入则实际只需 4 路。
完整信号清单见 `../../PROJECT_CONTEXT.md`。
