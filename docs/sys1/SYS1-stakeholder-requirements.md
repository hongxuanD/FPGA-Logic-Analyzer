# 干系人需求（SYS.1）

本文件记录原始诉求，用自然语言描述**为什么要做这个东西**。这一层允许模糊、
允许不可测量——把它变成可验证的条目是下一层（`../sys2/SYS2-system-requirements.md`）的工作。

干系人只有一位：项目作者，同时是这台仪器的唯一使用者。

## 需求

| ID | 需求 | 说明 |
| --- | --- | --- |
| `STK-001` | 能看到被测系统中 SPI 通信的实际信号 | 四条线 `SCK` / `MOSI` / `MISO` / `CS` 的电平变化，并能读出传输的字节内容，用于判断读写是否符合预期。**不限定于某一款芯片**，详见「目标设备」 |
| `STK-002` | 能把 SPI 传输放在上下文里看 | 在 SPI 四线之外同时采集相关信号，并与之共用同一时间基准，用来回答「主机为什么在这个时刻发起传输」。典型的相关信号是 SR150 的主机中断线，也可以是自行翻转的调试引脚。这要求通道数多于 4，且触发点之前的数据同样要保留——中断往往发生在触发之前 |
| `STK-003` | 用成熟的工具查看结果 | 不自行开发波形显示界面和协议解码器。这类软件已经很成熟，重写没有价值 |
| `STK-004` | 沿用已有的 FPGA 平台 | 硬件平台限定为手头的 Basys 3，**不更换 FPGA 板卡**。探针、测试夹、屏蔽线缆一类配件在必要时可以购置——信号完整性是首要风险，不应把改善它的手段排除在外 |
| `STK-005` | 等待时间不打断调试思路 | 从触发到在屏幕上看到波形，间隔要短。每次等十几秒会让人放弃使用这个工具 |
| `STK-006` | 不损坏被测设备 | 接入分析仪不应损坏被测设备或 Basys 3，也不应干扰被测电路的正常工作 |

## 目标设备

这台仪器是**通用工具**，不是为某一款芯片定制的。被测对象分两类：

**首个验证目标**

STM32 开发板。选它是因为手头就有、SPI 时钟可以在代码里任意调整，
便于从低速逐步加速摸清这套探针接线的实际能力。

**后续应用目标**

工作中实际会用到的设备，包括但不限于：

| 设备 | 类型 | 用途 |
| --- | --- | --- |
| QN9090 | NXP 低功耗蓝牙 MCU | 作为主机侧 |
| Raytac 模组 | 蓝牙模组 | 作为主机侧 |
| SR150 | NXP 超宽带（UWB）收发器 | 作为从机侧，与主机之间走 SPI |

主要关注的是**主机 MCU 与 SR150 之间的 SPI 通信**。

**2026-08-12 已核实实际配置**（查阅生产固件 `Nolo-Firmware/mk-nolo-firmware`）：
SCK 为 8.000 MHz，SPI Mode 0，8 位 MSB first，片选低有效。
与首个验证目标的速率一致，当前探针方案和采样率均能覆盖。
完整参数见 `../../PROJECT_CONTEXT.md`。

两点由此产生的实际影响：

- **总线上只有 SR150 一个从设备**，SPI 四线即可覆盖传输内容。但固件还操作 SR150
  的几根控制线，其中**主机中断线最有价值**——它能说明主机为何在某个时刻发起传输，
  只看 SPI 四线看不出这一点。合计 6 至 7 路信号值得采集，构成 `SYS-001` 通道数的依据。
  信号清单见 `../../PROJECT_CONTEXT.md`。
- 8 MHz 是**主机 QN9090 的 SPI 上限**，不是 SR150 的限制。若今后主机更换为
  基于 nRF52840 的 Raytac 模组（SPIM3 可达 32 MHz），速率假设需重新确认，
  届时应先修订本文件再向下传导。

## 目标协议

SPI 是**首个目标协议**，不是唯一目标。今后同样希望用它观察 I2C、UART 等
其他数字通信协议。

这一点不需要额外的设计投入：逻辑分析仪的采集侧本来就是协议无关的——
FPGA 只负责采样原始数字电平、触发、存储和上传，**并不知道什么是 SPI**。
协议知识全部位于上位机，sigrok 已经提供数十种解码器。

因此换协议时，通道数（I2C 要 2 路、UART 1 至 2 路，均少于 SPI）、
采样率（`SYS-009` 已要求可配置）、触发条件（`SYS-004` 的组合匹配可以表达
I2C 的起始条件，即 SCL 为高时 SDA 下降）都已被现有需求覆盖。

**唯一与协议相关的部分是触发。** 若今后要实现「触发在某个特定命令字节上」，
该功能必须理解 SPI 的时钟极性、位序与字节边界，届时应保持触发判定逻辑可替换，
而不是把协议知识散布到采集通路各处。

需要注意的是，本文件不写「系统应易于扩展」一类的条目——那不可验证，
也容易导致为想象中的需求做无用的抽象。可替换点应当在架构文档中逐个指名，
并各自说明其动机。

## 使用场景

作者在调试被测设备的 SPI 通信时，把探针接到四条 SPI 线上，让分析仪在片选拉低时
自动开始记录，传输结束后把数据取回电脑，在波形界面上看到解码出的字节序列，
对照预期内容判断是否一致。

首个验证目标的典型配置：SCK 最高约 8 MHz，单次传输规模在几十到几百字节。

## 非产品目标

以下是项目层面的目标，**不构成产品需求**，不会向下分解，也不作为验收依据。
记在这里是为了让后续读者理解某些决定的动机。

- 走一遍完整的 V 模型上游流程（SYS.1 到 SWE.2）。作者在工作中只承担过
  SWE.3 / SWE.4 / SWE.5，希望通过实际项目理解需求与架构层的做法。
- 复用 `FPGA-RS232` 项目积累的经验：可脚本重建的 Vivado 工程、共享上下文文档、
  参数化的 UART 实现。

## 明确排除的范围

写清楚不做什么，和写清楚做什么同样重要：

- **不做模拟量测量。** 这是逻辑分析仪，不是示波器。不测电压幅值、不看波形形状。
- **不做信号发生。** 所有探针引脚只读，不向被测电路输出任何激励。
- **不支持 5V 电路。** Basys 3 的 Pmod 不耐 5V，被测对象限于 3.3V 系统。
- **不追求商用仪器的速率。** 当前探针方案的能力上限由杜邦线决定。若后续目标设备
  确实需要更高速率，那是一次有意的范围扩展，应先修订本文件，而不是默认已覆盖。
- **不做长时间连续采集。** 板上没有外部 RAM，采集窗口是毫秒级的单次快照。
